# PTime V2.3 — Markov Chain Discrete-Time Manager

**Status:** SPEC RELEASED / IMPLEMENTATION PENDING  
**Version:** 2.3.0  
**Date:** 2026-10-03

## Theme

Manage time as a sequence of state transitions:

`T -> T+1 -> T+2 -> ...`

The important question is not only "is this action useful now?" but also:

> **What next state does this action make more likely?**

## Core model

Let:
- `S_t` = current state at decision boundary `T`;
- `A_t` = chosen action;
- `S_{t+1}` = next state.

Practical control model:

`P(S_{t+1} | S_t, A_t)`

This is a Markov-style operating approximation, not a claim that human behavior is literally memoryless. Relevant history — sleep debt, unfinished work, location, energy, attention and mission clarity — should be represented inside the current state.

## Discrete-time boundaries

A new `T` is created at meaningful decision boundaries, for example:
- wake;
- finish a task;
- arrive at a location;
- complete exploration;
- decide whether to continue or close;
- begin transit;
- enter recovery / sleep;
- restart after recovery.

The interval does not need to be a fixed number of minutes.

## State classes

- **ALPHATIME** — high-value execution, research, building, meeting, DD or focused learning.
- **RECOVERY** — sleep, rest, food, hydration or decompression that protects later execution.
- **EXPLORATION** — purposeful information acquisition with an explicit question or route to validate.
- **TRANSITION** — movement between known nodes with a clear next purpose.
- **DRIFT** — low-information, low-purpose continuation that tends to reproduce itself.

## Transition doctrine

### 1. T must be judged by T+1

Evaluate an action using:

`Immediate Value + Next-State Effect + Persistence + Opportunity Cost`

A small low-value action can be expensive if it raises the probability of several later low-value states.

### 2. No strong next T -> close

When there is no clear high-value next state:

`Close -> Recovery / Sleep -> Re-enter later`

Recovery is not "doing nothing." It is an active transition that can reset the next-state distribution.

### 3. Exploration has an exit condition

Exploration is useful while information gain is positive.

When the route, environment or ecosystem is understood and marginal information gain collapses:

`EXPLORATION -> CLOSE / PURPOSEFUL NEXT ACTION`

Do not let completed exploration silently become drift.

### 4. Break bad chains early

If the observed chain is:

`DRIFT -> more DRIFT -> delayed RECOVERY -> degraded next day`

insert a chain breaker:

`DRIFT -> CLOSE -> RECOVERY -> new decision boundary`

### 5. Optimize the chain, not isolated minutes

The objective is higher cumulative AlphaTime density across the sequence, while preserving enough recovery to make future AlphaTime likely.

## Minimal event schema

For each important boundary record:
- timestamp;
- `T` index / decision boundary;
- state class;
- location / context;
- intended action;
- expected `T+1`;
- actual `T+1`;
- information gain / value;
- whether to CONTINUE, CLOSE, RECOVER or TRANSITION.

## Field lesson

A completed city/route exploration can be valuable. The failure mode begins when information gain is already saturated but the chain continues without a purpose, pushing return, sleep and the next day's activation later.

V2.3 therefore makes **next-state quality** a first-class PTime variable.

## Relationship to V2.2

V2.2 asks how to make time more effective across execution, opportunity and recovery.

V2.3 adds a control layer for **how one time-state changes the next one**.

V2.2 = temporal operating layer.  
V2.3 = temporal state-transition manager.
